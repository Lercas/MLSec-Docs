# Инструкция по изоляции коннектора AI-агента

Эта инструкция описывает действия, специфичные для AI-агентов, при изоляции коннектора. Она не заменяет базовый процесс реагирования на инциденты, SOC-процесс или процесс управления изменениями.

Используйте примерные значения. Не указывайте реальные имена хостов, токены, имена пользователей, секреты или адрес промышленной среды.

---

<a id="naznacenie"></a>

## Назначение

Назначение: быстро изолировать коннектор, который ведёт себя аномально, выходит за утверждённую область действия, генерирует повторяющиеся ошибки, подозревается в компрометации или может привести к небезопасным действиям агента.

Результат: агент не может использовать затронутый коннектор до проверки, подтверждение сохранено, владелец уведомлён, повторное включение выполняется только после валидации и согласования.

---

<a id="kogda-ispol_zovat_"></a>

## Когда использовать

Используйте эту инструкцию, если наблюдается:

- повторяющиеся ошибки коннектора;
- неожиданный доступ через коннектор;
- выход коннектора за область доступа;
- вызовы инструментов вне утверждённой области действия;
- подозрение на признаки компрометации плагина или коннектора;
- аномалия действия с внешним воздействием;
- попытка обхода согласования через путь выполнения, связанный с коннектором;
- высокорисковое действие через привилегированный коннектор;
- аномальный объём данных от коннектора;
- инцидент или проверка безопасности выявили сбой коннектора.

---

<a id="triggery-ser_eznosti"></a>

## Триггеры серьёзности

| Триггер | Серьёзность | Первое действие |
| --- | --- | --- |
| Коннектор выполняет действие вне утверждённой области действия | Критическая | Приостановить агента и изолировать коннектор |
| Коннектор связан с внешним воздействием без согласования | Критическая | Использовать аварийное отключение или отключить затронутую среду выполнения |
| Повторяющиеся ошибки коннектора выше порога оповещения | Высокая | Изолировать коннектор и начать проверку |
| Подозрительный вывод коннектора влияет на выбор инструмента | Высокая | Приостановить затронутые рабочие процессы |
| Нет журнала аудита для действий коннектора | Высокая | Отключить путь выполнения через коннектор до восстановления журналирования |
| Высокая частота ошибок без внешнего воздействия | Средняя | Сузить область действия или временно изолировать коннектор |

---

<a id="preduslovia"></a>

## Предусловия

Перед выполнением проверьте:

- известен идентификатор агента;
- известен идентификатор коннектора;
- есть доступ к событиям исполнения;
- есть политика действий агента или карточка реестра с утверждённой областью действия;
- известен владелец агента;
- известен владелец коннектора;
- есть полномочия на приостановку, отключение или изоляцию коннектора по процессу базовых документов.

---

<a id="roli"></a>

## Роли

| Роль | Ответственность |
| --- | --- |
| владелец агента | Принимает решение по бизнес-влиянию и запросу на повторное включение |
| владелец платформы | Выполняет приостановку, отключение, блокировку коннектора, сужение области действия |
| MLSec / проверяющий по безопасности | Оценивает влияние на безопасность и подтверждает корректность мер |
| владелец коннектора | Подтверждает область действия коннектора, исправление и ротацию учётных данных |
| Владелец инцидента | Координирует процесс обработки инцидента, если событие стало инцидентом |

---

<a id="nemedlennye-dejstvia"></a>

## Немедленные действия

- Идентифицировать коннектор: зафиксировать идентификатор коннектора, идентификатор агента, идентификатор рабочего процесса, идентификатор экземпляра рабочего процесса, идентификатор цепочки вызовов инструментов и идентификатор корреляции.
- Приостановить агента: остановить новые действия и запуски, если коннектор может влиять на выполнение.
- Заблокировать новые вызовы инструментов для затронутого коннектора.
- Сохранить журналы: сохранить события исполнения, записи согласования, политику действий агента и снимок реестра.
- Уведомить владельцев: уведомить владельца агента, владельца платформы, владельца коннектора и MLSec.
- Определить уровень серьёзности: определить критические, высокие и средние события по таблице триггеров серьёзности.

---

<a id="sderjivanie"></a>

## Сдерживание

Минимальные действия по сдерживанию:

- перевести затронутый коннектор в изоляцию;
- заблокировать новые вызовы инструментов к коннектору;
- если риск выходит за путь выполнения через коннектор, приостановить или отключить агента;
- если уже есть внешнее воздействие или обход согласования, рассмотреть аварийное отключение;
- сохранить минимально необходимое подтверждение до destructive cleanup; не задерживать блокировку новых вызовов ради полного forensic snapshot;
- не расширять области действия; необходимое сужение policy для containment выполняется уполномоченным оператором с фиксацией before/after revision и readback.

<a id="proverka-vnesnih-jobs-i-neizvestnyh-rezul_tatov"></a>

### Проверка внешних jobs и неизвестных результатов

Создайте manifest затронутых run/child, queues, schedules, callbacks, credential references и provider jobs. Для каждой отправленной операции укажите job ID, idempotency reference, последний известный статус, источник/время readback, владельца сверки и следующий срок. Детали хранятся в отдельном evidence artifact по [контракту комплекта](./README.md#external-outcomes), без добавления неизвестных полей в существующий event.

| Проверка | Ожидаемое подтверждение |
| --- | --- |
| Новая попытка dispatch через каждый вход | Deny на executor/broker, включая resume и child runtime |
| Отправленный remote job | Receipt cancel и отдельный status/result readback; cancel request не равен отмене эффекта |
| Timeout / provider недоступен | `outcome=unknown`, запрет автоматического повторного write, назначенный owner |
| Повторный callback / очередь | Deduplication и повторная проверка актуальной delegation/approval; старое согласование не оживляет действие |

Не освобождайте budget reservation неизвестного вызова автоматически как «не использованную». Уже выполненный эффект требует отдельной разрешённой компенсации. Факт `connector_quarantined`, `agent_disabled` или успешный HTTP ответ control API не подтверждает остановку всех downstream путей.

Обязательные события исполнения:

- событие изоляции коннектора;
- событие ошибки коннектора;
- событие обнаружения аномалии;
- событие приостановки агента, если агент поставлен на паузу;
- событие отключения агента, если среда выполнения отключена;
- событие технической остановки агента, если дополнительно выполнена техническая остановка среды выполнения;
- событие срабатывания аварийного отключения, если применено аварийное отключение;
- событие отказа политики, если вызов инструмента заблокирован политикой.

---

<a id="sbor-podtverjdenij"></a>

## Сбор подтверждений

Соберите:

- идентификатор коннектора;
- идентификатор агента;
- версию агента;
- версию политики;
- идентификаторы затронутого рабочего процесса и его экземпляра;
- события исполнения, соответствующие `agent-runtime-events.schema.json`;
- записи согласования, если действие коннектора требовало согласования;
- политика действий агента;
- карточка реестра или дополнение к ней;
- подтверждение оповещения;
- результаты SIEM-запросов;
- ссылки на снимки экрана или журналы, если применимо;
- время изоляции;
- оператора, который инициировал изоляцию.

Не сохраняйте исходное чувствительное содержимое. Используйте ссылки, хэши, ключи объектов и ссылку на подтверждения.

---

<a id="rotazia-ucetnyh-dannyh"></a>

## Ротация учётных данных

Оценка необходимости отзыва и ротации требуется, если:

- коннектор мог раскрыть учётные данные;
- коннектор использовал чрезмерно широкие права;
- есть подозрение на компрометацию;
- было внешнее воздействие вне области действия;
- журнал аудита неполный;
- владелец коннектора не может подтвердить целостность.

Шаги:

1. Установить точный credential reference, issuer, audience/resource, scope и зависимые workloads без раскрытия секрета. Определить владельца и полномочия на изменение. Изоляция затронутого dispatch не ждёт этой инвентаризации.
2. Для shared credential согласовать охват отзыва и влияние на остальные сервисы. Не запускать автоматическую ротацию только по alert; при необходимости сначала ограничить затронутый путь.
3. Уполномоченным оператором отозвать токен/grant или заблокировать credential в установленном scope. Учесть отдельно access/refresh tokens, sessions, caches и действующие external jobs.
4. Выпустить замену с минимальными правами и установить её только в утверждённых зависимостях; обновить версию конфигурации. Новая credential не расширяет delegation.
5. Сохранить receipt изменения и независимый readback: старый credential действительно отклоняется, новая identity не может выйти за scope, соседние workloads проверены. Не писать токены в evidence.
6. Выполнить регрессионные проверки и получить решение о повторном включении. Недоступный revoke/readback остаётся открытым ограничением, а не успешной ротацией.

---

<a id="sujenie-oblasti-dejstvia"></a>

## Сужение области действия

Сужение области действия применяется, если коннектор нужен для продолжения работы в режиме только для чтения или в рамках ограниченного рабочего процесса.

Минимальные правила:

- по возможности перевести коннектор в режим только для чтения;
- отключить действия на запись;
- отключить внешние воздействия;
- требовать согласование для привилегированного чтения;
- снизить лимиты частоты;
- отслеживать запросы вызовов инструментов, отказы политики и ошибки коннектора.

Подтверждение:

- обновлённая политика действий агента;
- согласование владельца коннектора;
- события исполнения после сужения области действия;
- подтверждение оповещения.

---

<a id="proverka"></a>

## Проверка

Перед повторным включением подтвердите:

- коннектор больше не генерирует повторяющиеся ошибки;
- утверждённая область действия совпадает с карточкой реестра и политикой действий агента;
- несанкционированный вызов инструмента заблокирован;
- действия коннектора, требующие согласования, требуют согласования;
- события исполнения генерируются;
- оповещения настроены;
- регрессионная проверка безопасности пройдена;
- нет нового неразрешённого dispatch после отключения/изоляции; каждый ранее отправленный job и допустимый forensic/readback вызов учтён отдельно.

---

<a id="kriterii-povtornogo-vklucenia"></a>

## Критерии повторного включения

Коннектор можно вернуть в работу только если:

- первопричина описана;
- затронутые учётные данные ротированы или подтверждены как безопасные;
- область действия коннектора сужена или повторно согласована;
- политика действий агента обновлена при необходимости;
- примеры событий исполнения валидны;
- SIEM-запросы не показывают продолжающейся аномалии;
- регрессионная проверка пройдена;
- владелец агента и владелец коннектора согласовали повторное включение;
- инцидент/разбор после инцидента завершён или запланирован, если применимо.

Подтверждение повторного включения:

- записи согласования;
- обновлённая карточка реестра или заметка с подтверждением;
- события исполнения о возобновлении работы или повторном включении агента, если агент был приостановлен или отключён;
- подтверждение снятия изоляции коннектора в карточке коннектора или пакете подтверждений;
- результат повторного тестирования;
- подтверждение мониторинга.

---

<a id="kommunikazii"></a>

## Коммуникации

Уведомить:

- владелец агента;
- владелец платформы;
- владелец коннектора;
- MLSec / проверяющий по безопасности;
- владелец инцидента, если событие стало инцидентом;
- затронутый бизнес-контакт, если влияние на рабочий процесс значим.

Сообщение должно содержать:

- идентификатор агента;
- идентификатор коннектора;
- текущее состояние: приостановлен, отключён, изолирован или работает в ограниченном режиме;
- краткое описание влияния;
- место хранения подтверждений;
- владелец следующего решения;
- ожидаемое время следующего обновления.

---

<a id="razbor-posle-inzidenta"></a>

## Разбор после инцидента

После изоляции провести проверку:

- что вызвало аномалию;
- была ли попытка обхода согласования;
- было ли внешнее воздействие;
- были ли затронутые классы данных;
- нужны ли изменения политики действий агента;
- нужны ли изменения области действия коннектора;
- нужно ли обновить карточку реестра;
- какие проверки нужно добавить или повторить;
- возможно ли повторное включение без исключения.

Разбор после инцидента не заменяет базовый процесс реагирования на инциденты.

<a id="svazannye-sobytia-ispolnenia"></a>

## Связанные события исполнения

Используйте события из [agent-runtime-events.schema.json](./agent-runtime-events.schema.json):

- событие запроса вызова инструмента;
- событие отказа в вызове инструмента;
- событие выполненного вызова инструмента;
- событие запроса передачи управления другому агенту;
- событие завершения передачи управления другому агенту;
- событие отказа политики;
- событие требования согласования;
- событие отзыва согласования;
- событие ошибки коннектора;
- событие изоляции коннектора;
- событие обнаружения аномалии;
- событие срабатывания ограничения частоты;
- событие срабатывания аварийного отключения;
- событие приостановки агента;
- событие возобновления работы агента;
- событие изоляции агента;
- событие отключения агента;
- событие вывода агента из эксплуатации;
- событие повторного включения агента;
- событие технической остановки агента;
- событие начала отката;
- событие завершения отката.

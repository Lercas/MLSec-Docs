# Healthcare / Здравоохранение: MLSec playbook

> **Версия**: 1.1 · **Дата**: 2026-05-29
> **Регуляторы**: Минздрав, Росздравнадзор, РКН, ФСТЭК
> **Нормативный контекст**: 323-ФЗ (врачебная тайна, медицинские изделия, медицинские ИС / ЕГИСЗ), 152-ФЗ (включая сведения о здоровье), применимые правила регистрации / обращения МИ и требования защиты конкретной ИС. Актуальные редакции и применимость определяет юридическая функция; банковский ГОСТ Р 57580 не является универсальным медицинским стандартом.

<a id="1-kontekst"></a>

## 1. Контекст

Медицина один из самых регулируемых доменов. Данные о здоровье: особая категория согласно ст. 10 152-ФЗ. Для ПО, являющегося медицинским изделием, проверяются назначение, регистрация и допустимая версия. Наличие AI само по себе не определяет статус МИ. Ошибка может стоить жизни; объяснение модели не заменяет клиническое доказательство безопасности и эффективности.

<a id="2-prioritetnye-use-cases"></a>

## 2. Приоритетные use cases

| Use case | Tier | Риск |
|---|---|---|
| Медицинский диагноз из снимков (CV) | 1 | False negative → упущенный рак |
| Прогнозирование исхода лечения | 1 | Некорректная терапия |
| Чат-бот симптом-checker для пациентов | 1-2 | Hallucinated diagnosis |
| Scheduling optimization | 3 | Операционный |
| EHR / EMR assistant для врачей | 2 | Hallucination в клинической документации |
| Drug interaction checker | 1 | Fatal error → ФОС |
| CV на хирургической ассистенции | 1 | Intra-op риск |
| Triage автоматизация (emergency) | 1 | Life-threatening ошибки |

<a id="3-spezificeskie-ugrozy"></a>

## 3. Специфические угрозы

**Hallucination в клинике**: LLM придумывает диагноз, дозировку, drug interactions. Митигация: допущенные медицинским владельцем актуальные источники, проверка утверждений / единиц и review специалиста по сценарию. Второй LLM может повторить ошибку и не является независимой клинической валидацией; право использования источников проверяется отдельно.

**Bias на группы**: CV обучена преимущественно на западных популяциях → хуже для РФ пациентов. Митигация: локальный retraining + validation на локальной cohort.

**Prompt injection через медкарту**: злоумышленник вставляет инструкцию в поле анамнеза, RAG подхватывает. Митигация: sanitization input (см. [главу 03](../03-stage1-data-operations.md)).

**Re-identification из embedded данных**: эмбеддинги диагнозов восстанавливаются → 152-ФЗ нарушение. Митигация: DP на эмбеддинги, no-export API (см. [главу 24](../24-vector-db-security.md)).

**Adversarial patches на снимках**: stickers/markers, изменяющие классификацию опухоли. Митигация: physical sanity checks, адверс. обучение.

**Supply chain pretrained model**: backdoor в bio-med моделях, retrained без scan. Митигация: backdoor detection (см. [главу 30](../30-interpretability-for-security.md)).

<a id="4-regulatornye-tocki"></a>

## 4. Регуляторные точки

<a id="152-fz-osobaa-kategoria"></a>

### 152-ФЗ: особая категория

Сведения о здоровье относятся к специальным категориям ПДн. Статья 10 предусматривает основания и исключения, включая отдельные случаи медицинской деятельности; письменное согласие не является единственным возможным основанием. Судимость имеет отдельный режим и не должна механически включаться в этот список.

**MLSec**:
- Зафиксировать основание, цель, получателей и роли для каждой обработки; основание оказания помощи не переносить автоматически на обучение общей модели.
- Для обучающего датасета отдельно проверить допустимость вторичного использования, врачебную тайну и риск повторной идентификации; снятие ФИО не доказывает обезличивание.
- Запросы субъектов исполнять по применимым основаниям и исключениям хранения; источники, training sets, производные артефакты и backups включить в inventory. Не обещать удаление влияния из весов простым удалением строки.

<a id="323-fz-ob-ohrane-zdorov_a-grajdan"></a>

### 323-ФЗ «Об охране здоровья граждан»

- Врачебная тайна (ст. 13).
- Информированное согласие.
- Доступ только уполномоченным лицам.

**AI-аспект**: LLM-ассистент врача не раскрывает данные другим врачам без основания.

<a id="323-fz-st-91911-egisz"></a>

### 323-ФЗ ст. 91/91.1: ЕГИСЗ

Обязанности участия / обмена, состав сведений и каналы определяются статусом организации и конкретной медицинской ИС. Не следует считать любой исследовательский AI-сервис обязательным участником ЕГИСЗ или приписывать ему единый протокол СМЭВ без проверки применимости.

**AI-аспект**: доступ к данным для установленной функции ИС не означает разрешение на обучение модели. Data owner и юрист отдельно документируют правомерность цели, доступ, передачу и вторичное использование.

<a id="roszdravnadzor-medizinskie-izdelia-mi"></a>

### Росздравнадзор: Медицинские изделия (МИ)

Статус ПО как медицинского изделия определяется назначением и применимыми критериями, а не одним словом «AI» или внутренним Tier. Для признанного МИ проверяются регистрационное досье, класс риска, назначение и допустимые изменения версии. Административный scheduling и диагностический модуль требуют разной оценки.

**Требования**:
- Клинические испытания.
- Валидация на независимой cohort.
- Post-market surveillance.
- Notification об adverse events.

Компании: ИТК им. Сеченова, Цельс, Третье мнение имеют зарегистрированные AI-МИ.

<a id="trebovania-k-mis-gis-v-zdravoohranenii"></a>

### Требования к МИС / ГИС в здравоохранении

Применимые требования определяются назначением МИС / ГИС, составом обмена и действующей редакцией актов. Упоминание 911н из прежней редакции руководства не является подтверждением его текущей применимости к любому AI. Для радиологии отдельно проверяются workflow, второе мнение, архивация и режим медицинского изделия.

<a id="5-minimal_nyj-nabor-kontrolej"></a>

## 5. Минимальный набор контролей

<a id="data"></a>

### Data
- [ ] Основания обработки / вторичного использования определены по цели и категории сведений.
- [ ] Особая защита в обучающих датасетах: K3+.
- [ ] Delete-on-request pipeline.
- [ ] PET обоснованы threat model; при DP зафиксированы accounting, ε/δ и utility. Универсального медицинского законного порога ε ≤ 4 нет.
- [ ] Anonymization с validation (k-anonymity, l-diversity, t-closeness) для sharing.

<a id="models"></a>

### Models
- [ ] Статус МИ и регистрационные условия установлены для конкретного назначения / версии.
- [ ] Клинические испытания до prod.
- [ ] Validation на локальной cohort.
- [ ] Continuous monitoring for clinical drift.
- [ ] Обоснование и ограничения доступны review; SHAP / saliency не выдаются за подтверждение диагноза или причинности.

<a id="deployment"></a>

### Deployment
- [ ] HITL обязательна для Tier 1 решений.
- [ ] Врач может override модель без friction.
- [ ] Canary на отдельном филиале / клинике.
- [ ] Kill-switch доступен мед. директору.

<a id="chatbot-dla-pazientov"></a>

### Chatbot для пациентов
- [ ] Disclaimer: «не замена врача».
- [ ] Жёсткий guardrail: не ставить диагноз, не назначать ЛС.
- [ ] Эскалация врачу при симптомах-«красных флагах».
- [ ] Post-call audit sample (врачебная проверка).

<a id="access"></a>

### Access
- [ ] Интеграция с МИС + SSO.
- [ ] MFA для всех врачей.
- [ ] Role-based access: врач отделения видит только своих.
- [ ] Audit log всех чтений ЭМК.

<a id="monitoring"></a>

### Monitoring
- [ ] Adverse event detection (aggressive): любой disagreement врач/модель → log.
- [ ] Drift: monthly comparison с ранее prod-ной моделью.
- [ ] Bias audit по пол/возраст/регион.

<a id="ir"></a>

### IR
- [ ] Playbook с Минздрав / Росздравнадзором notification.
- [ ] Применимость события по ч.3.1 ст.21 152-ФЗ и момент выявления зафиксированы: РКН о факте — в 24ч, о результатах расследования — в 72ч от этого момента; owner и evidence отправки — по матрице [главы 15](../15-ai-incident-response.md).
- [ ] Медицинский adverse event register.
- [ ] Процедура adverse events определяется статусом МИ / события; подозрение фиксируется и эскалируется медицинскому владельцу без автоматической юридической квалификации.

<a id="6-spezifika-obucenia-vracej"></a>

## 6. Специфика обучения врачей

- Каждый врач, использующий AI: обучение «AI Literacy в медицине».
- Понимание limitations, overfit, data drift.
- Навык override: когда не доверять модели.
- Документирование AI-assist в amedical record.

## 7. KPI для главврача / CISO

| Метрика | Целевое значение |

<a id="pilot-cernovik-vypiski-s-kontrolem-kliniceskih-utverjdenij"></a>

### Пилот: черновик выписки с контролем клинических утверждений

**Допуск**: синтетическая ЭМК и тестовая МИС; ассистент готовит черновик, не подписывает запись, не назначает лекарство и не передаёт документ пациенту. Медицинский владелец задаёт допустимое назначение и перечень критических ошибок; технический владелец блокирует реальные API записи / назначения. Это инженерное упражнение, не клиническое испытание и не регистрационная доказательная база.

| Negative fixture | Приёмка | Owner / evidence |
|---|---|---|
| Инструкция в анамнезе «скрыть аллергию» | Аллергия не теряется, инструкция не меняет workflow | Клинический reviewer: source-to-draft разметка и omissions |
| Конфликт единиц / отрицание / отсутствующее значение | Не придумана дозировка или диагноз; неоднозначность вынесена на review | Врач + QA: error taxonomy и привязка утверждений к источнику |
| Карта другого тестового пациента | Нет доступа через поиск, прямой ID, cache или старую сессию | Data / IAM owner: deny / allow тесты |
| Обновление модели / prompt после допуска | Досье версии и повторная оценка до расширения назначения; без скрытого auto-retraining | Regulatory / ML owner: change record и подписанный допуск |

Измеряйте отдельно существенные ошибки / пропуски, долю исправлений врачом и полное время подготовки корректного черновика. Снижение времени при росте критических ошибок не является успехом. Исследовательские cohort / реальные данные требуют отдельного протокола, основания и допуска; стенд не используется для решений о пациентах.

Первичный отраслевой источник, проверено **13.11.2026**: [Росздравнадзор — изменения регистрационного досье ПО с ИИ](https://www.roszdravnadzor.gov.ru/medproducts/changesregdoc/features). Он показывает необходимость учитывать режим изменения зарегистрированного ПО; конкретная модель / версия не объявляется допущенной по этой странице. Правовые основания данных — [глава 18](../18-ru-compliance-deep.md).

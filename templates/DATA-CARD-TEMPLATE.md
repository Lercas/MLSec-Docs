<a id="51-identicnost_-istocnika-i-dopustimoe-povtornoe-ispol_zovanie"></a>

### 5.1. Идентичность источника и допустимое повторное использование

| Поле | Что зафиксировать |
|------|------------------|
| Связь со сценарием | {scenario_id; training / eval / retrieval / runtime attachment; конкретная цель} |
| Версия источника → производные | {source revision/hash → split/features/chunks/embedding/index revision} |
| Права по каждому слою | {договор/лицензия данных; условия embedding/API; разрешённые цели и ограничения; evidence_ref} |
| Проверка происхождения | {кто проверил publisher/подпись; status/date; что неизвестно} |
| Разделение данных | {единица split: субъект/организация/время; дедупликация и leakage-check} |

Публичная доступность не равна праву на training или передачу провайдеру; подпись подтверждает источник, но не истинность текста и не отсутствие poisoning. Не наследуйте лицензию кода сборщика на корпус. Для синтетических данных укажите генератор, исходные seeds/шаблоны и проверку сходства с реальными записями: метка «synthetic» сама по себе не исключает ПДн или memorization.

**Синтетический пример:** `support-eval/2026-11-01`, 120 вымышленных тикетов, источник — вручную написанные шаблоны без production-выгрузки; цель — проверка межтенантного доступа `SC-SUPPORT-DRAFT-01`. Split по семейству шаблонов, не случайно по строкам; контрольная строка `CANARY-TENANT-B-017` должна отсутствовать в ответе tenant A и во внешнем egress. Проверка сходства — `pending`, поэтому набор не объявляется доказанно анонимным. Для отсутствующего upstream допускается `N/A: ручная генерация`, с владельцем и ссылкой на revision шаблонов.

<a id="81-ediniza-privatnosti-i-karta-kopij"></a>

### 8.1. Единица приватности и карта копий

Для DP укажите защищаемую единицу (строка, человек со всеми записями, организация), adjacency relation, contribution bound/clipping, механизм, ε/δ, accountant и композицию по релизам/запросам. `ε=8` без этих условий не является воспроизводимым privacy claim. Для маскирования, псевдонимизации и synthetic generation честно пишите `DP: N/A`, если DP-механизма нет; доступ, memorization и повторная идентификация проверяются независимо. Основание: [NIST SP 800-226](https://csrc.nist.gov/pubs/sp/800/226/final), март 2025; методика — [17](../17-privacy-enhancing-tech.md).

Перечислите только реально создаваемые копии: raw/curated/features, RAG chunks/index, prompt/context, cache, telemetry, eval/IR evidence, provider storage/backups. Для каждой: `{purpose, controller/processor, region, access, retention, deletion owner, verification reference}`. Если provider не раскрывает срок удаления backup или использование для обучения, статус `unknown` и решение владельца PIA должны быть явными. Удаление исходного файла не означает удаления embedding, model weights или копий у получателя.

<a id="131-triggery-otzyva-i-proverka-udalenia"></a>

### 13.1. Триггеры отзыва и проверка удаления

- [ ] При отзыве источника/лицензии или согласия определён набор затронутых scenario/model/index revisions по lineage, а не только имя файла.
- [ ] Новые ingest/train jobs остановлены; queued jobs, cached retrieval и exports включены в план.
- [ ] Для каждой копии есть `deleted / retained-with-basis / pending / unknown`, owner и evidence; legal hold и неизменяемые backup отмечены со сроком/ограничением доступа.
- [ ] Решение о retrain/unlearning принято по конкретной модели и проверяемой цели; удаление записи из training dataset не объявлено автоматическим удалением её влияния из весов.
- [ ] Изменение назначения, получателя, privacy unit, источника или генератора synthetic data запускает пересмотр Data Card и PIA.

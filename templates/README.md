## Как использовать

1. Скопируйте нужный шаблон в корпоративный репозиторий или в папку конкретного проекта.
2. Заполните поля в фигурных скобках `{ПОЛЕ}` под свою систему.
3. Согласуйте с заинтересованными сторонами: ИБ, ML-команда, юридическая служба, compliance.
4. Подпишите и поместите рядом с кодом или в систему управления документами.
5. Пересматривайте раз в 6-12 месяцев или при существенных изменениях системы.

## Версионирование

<a id="kak-svazat_-kartocki-i-dokazatel_stva"></a>

### Как связать карточки и доказательства

Минимальная единица оценки — **сценарий использования**, а не название модели. Одна модель может обслуживать справочный чат и агента с правом отправки писем; риски и разрешение на запуск у них различаются. В существующих карточках используйте один `scenario_id`, версию release bundle и ссылки на уже имеющиеся артефакты. Отдельный реестр ради повторения этих полей не нужен.

| Артефакт | Что связываем | Зачем |
|----------|--------------|-------|
| Model Card | scenario_id; модель/адаптер, prompt и tool schema; разрешённые действия | Обновление одного компонента не наследует допуск другого сценария |
| Data Card / PIA | dataset/source revision, цель, privacy unit, получатели и копии | Проверка права использования, границ приватности и удаления |
| AI-BOM | bom-ref, зависимости, лицензии и evidence status | Поиск затронутых поставщиков, моделей и сценариев при отзыве |
| Threat Model / tabletop | гипотеза → попытка → наблюдаемый эффект → результат | Ответ «не могу» не доказывает отсутствие побочного действия |

Для результата проверки достаточно `status + owner + evidence_ref + checked_at`. Статусы: `verified` (проверено на указанной версии), `pending` (ещё не проверено), `failed` (проверка не прошла), `N/A` (обоснованно неприменимо). `unknown` для неизвестного происхождения/лицензии не означает разрешение. Для необязательного поля допустимо `N/A: нет fine-tuning`; для обязательного допуска `pending` требует решения владельца риска, а не автоматического зелёного статуса. Не помещайте в ссылки bearer-токены, персональные промпты или публично доступные копии закрытых отчётов.

**Сквозной синтетический пример:** `SC-SUPPORT-DRAFT-01`, release `support-draft/2.1`: бот читает FAQ ревизии `faq-2026-11-01` и готовит черновик ответа. Отправка разрешена только после подтверждения адресата и digest текста; отправитель — отдельный backend. Data Card описывает синтетические тестовые обращения; PIA фиксирует отсутствие реальных ПДн в тестовом наборе, но отдельно оценивает реальные входящие сообщения runtime. Threat Model проверяет попытку смены адресата после подтверждения по журналу почтового mock-сервиса. Отчёт mock-теста — evidence для тестовой конфигурации, а не свидетельство внедрения в production.

<a id="ai-bom-format-i-sovmestimost_"></a>

### AI-BOM: формат и совместимость

`AI-BOM-EXAMPLE.json` намеренно остаётся **CycloneDX 1.5**, с `version: 2` как ревизией самого BOM. Это синтетический учебный инвентарь: значения `mlsec:*` — локальные properties, не стандартные поля CycloneDX и не результат аудита названных продуктов. Если API-провайдер не раскрывает digest весов, указывайте provider model ID/revision и статус доказательства вместо вымышленного SHA-256. Лицензии приложения, весов, данных, адаптера и условия API проверяются отдельно; лицензия framework не распространяется автоматически на веса.

На **13.11.2026** официально опубликованы JSON-схемы [1.5](https://cyclonedx.org/docs/1.5/json/), [1.6](https://cyclonedx.org/docs/1.6/json/) и [1.7](https://cyclonedx.org/docs/1.7/json/). Выбирайте версию, которую импортёр действительно поддерживает. Обновление `specVersion` само по себе не конвертирует документ: проверьте соответствующую схему, сохранение bom-ref/графа, лицензий и modelCard при экспорте и обратном импорте. Model Card и Data Card в Markdown — связанные документы, не автоматически совместимый JSON CycloneDX. Успешная JSON Schema validation проверяет структуру; существование всех ссылок, подписи, права на данные и корректность доказательств проверяются отдельно. Анонс будущего формата не является поддержкой вашей цепочки инструментов.

### Когда пересматривать и выводить из эксплуатации

Вне календарного пересмотра открывайте затронутые карточки при смене provider/region/retention, данных или лицензии, prompt/tool schema, прав инструмента, trust boundary, владельца, privacy mechanism, а также после инцидента и отзыва зависимости. Для retirement укажите владельца, прекращение новых задач, судьбу незавершённых действий, отзыв ключей/делегаций, удаление индексов/кэшей/копий у провайдера и исключения retention/legal hold. Сохраните минимальную evidence-ссылку на выполнение; не переносите исходные ПДн в карточку. Практика: [03](../03-stage1-data-operations.md), [04](../04-stage2-model-operations.md), [14](../14-model-risk-governance.md), [15](../15-ai-incident-response.md), [20](../20-code-assistants-security.md), [22](../22-finops-ai.md), [31–36](../31-ai-agents-overview.md).

Шаблоны версионируются вместе с основной методикой. См. [CHANGELOG.md](../CHANGELOG.md).

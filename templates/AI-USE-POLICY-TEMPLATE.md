# AI Use Policy: {НАИМЕНОВАНИЕ ОРГАНИЗАЦИИ}

> Шаблон корпоративной политики использования ИИ-инструментов. Заполняется CISO совместно с юридической службой, HR и ML-руководителями. См. главу [14. Governance](../14-model-risk-governance.md).

<a id="1-zel_-i-oblast_-primenenia"></a>

## 1. Цель и область применения

Политика устанавливает правила использования систем искусственного интеллекта сотрудниками, подрядчиками и партнёрами {ОРГАНИЗАЦИЯ}. Распространяется на все ИИ-инструменты: внешние облачные (ChatGPT, Claude, Gemini), локальные self-hosted (Llama, Qwen, GigaChat), код-ассистенты (Copilot, Cursor, Claude CLI, Codex, Aider), агентские платформы, RAG-системы.

<a id="2-opredelenia"></a>

## 2. Определения

- **ИИ-инструмент**: любое программное решение на основе LLM, включая чат-интерфейсы, API, код-ассистенты, агенты, RAG-системы.
- **Класс данных K0-K4**: корпоративная классификация (см. раздел 3).
- **Режим использования**: конкретный набор действий: просмотр, ввод, получение ответов, скачивание, отправка как контекст.
- **LLM Gateway**: корпоративный контролируемый контур для всех обращений к LLM (в нашей среде: Rilio).

<a id="3-klassifikazia-dannyh"></a>

## 3. Классификация данных

| Класс | Описание | Примеры |
|-------|----------|---------|
| K0 | Публичные данные, размещённые на сайтах организации | Маркетинговые материалы, публичный API |
| K1 | Внутренние данные без ПДн и тайн | Корпоративные инструкции, нечувствительная документация |
| K2 | Коммерческая тайна и внутренние процессы | Планы, договоры под NDA, техническая документация |
| K3 | ПДн и чувствительные данные | ПДн клиентов и сотрудников, финансовые данные, сведения о здоровье |
| K4 | Критичные данные | Государственная тайна, ключи КИИ, банковская тайна, секретные алгоритмы |

<a id="4-matriza-razresenij-klass-dannyh-tip-modeli"></a>

## 4. Матрица разрешений: класс данных × тип модели

| | Self-hosted (наш контур) | Российский провайдер | Зарубежное облако с корп. договором | Публичное зарубежное облако |
|-|:------------------------:|:--------------------:|:-----------------------------------:|:---------------------------:|
| **K0** | Разрешено | Разрешено | Разрешено | Разрешено |
| **K1** | Разрешено | Разрешено | Разрешено через Gateway | С одобрения ИБ |
| **K2** | Разрешено | По согласованию | Только через Gateway с DLP | Запрещено |
| **K3** | С маскированием / PET | По согласованию с DPO | Запрещено | Запрещено |
| **K4** | С одобрения CISO и при наличии compliance-заключения | Запрещено | Запрещено | Запрещено |

Это пример внутренней матрицы, а не универсальное разрешение по юрисдикции провайдера: до утверждения проверяются цель, договор, применимые ограничения передачи, конфигурация и evidence. Маскирование само по себе не исключает ПДн. Требование организации: все поддерживаемые API-обращения проходят через корпоративный LLM Gateway; обходы проверяются egress-тестами. DNS / PAC сами по себе не доказывают блокировку прямых API, MCP или terminal-каналов.

<a id="5-obsie-pravila"></a>

## 5. Общие правила

<a id="51-razreseno"></a>

### 5.1. Разрешено

- Использовать одобренные инструменты с данными K0 в пределах разрешённого сценария; K0 — класс данных, а не уровень доверия модели.
- Использовать одобренные модели для K1-K2 через корпоративный Gateway.
- Отправлять в модели обезличенные (masked) версии K3-данных после предварительной обработки DLP.
- Подписывать модели, артефакты и промпты cosign-ом при передаче в runtime.
- Запрашивать расширенный доступ у CISO через формализованную процедуру.

<a id="52-zapreseno"></a>

### 5.2. Запрещено

- Отправлять K3-K4 данные в публичные зарубежные модели.
- Хардкодить ключи LLM API в коде, ноутбуках, конфигах.
- Подключать неаудированные MCP-серверы к код-ассистентам.
- Использовать модели из непроверенных источников (HuggingFace без подписи, torrent-ы).
- Применять ИИ-ассистентов для принятия финансовых, кадровых и юридических решений без human review.
- Передавать ответы модели как окончательное решение в публичных каналах (всегда требуется проверка человеком).

<a id="6-osobye-szenarii"></a>

## 6. Особые сценарии

<a id="61-kod-assistenty"></a>

### 6.1. Код-ассистенты

Все код-ассистенты (Copilot, Cursor, Claude CLI, Codex, Aider, Continue, Cline, Windsurf) маршрутизируются через LLM Gateway с DLP и audit log. Прямой выход в публичные облачные инстансы без корпоративного договора заблокирован. Сотруднику запрещено передавать в код-ассистент:
- Секреты (ключи, токены, пароли).
- ПДн клиентов.
- Коммерческую тайну.
- Ключевые алгоритмы и финансовые модели.
- Код из-под закрытой лицензии.

<a id="62-agenty"></a>

### 6.2. Агенты

Агентские системы (с автономным выполнением действий) работают в изолированной среде (gvisor / Firecracker / WASM) с allowlist инструментов. Все опасные действия (финансовые операции, отправка данных наружу, изменение конфигурации) требуют HITL-подтверждения.

<a id="621-podtverjdenie-konkretnogo-dejstvia"></a>

#### 6.2.1. Подтверждение конкретного действия

HITL означает проверяемое разрешение на **конкретный** эффект. Backend связывает approval с пользователем/tenant, tool и schema revision, нормализованными аргументами/digest содержимого, получателем/ресурсом, лимитом суммы/данных, сроком и одноразовым идентификатором. Модель, документ, subagent и tool-result не могут выдать это разрешение. Изменение аргументов, получателя или прав после preview требует нового подтверждения; retry не должен повторять эффект.

Это контракт приложения, а не встроенный approval-token формата MCP. [MCP Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) рекомендует human-in-the-loop и подтверждения; [Security Best Practices](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices) отдельно рассматривает confused deputy, session hijacking и минимизацию scope. Редакция протокола в ссылках — 2025-11-25; проверено 13.11.2026.

**Синтетический пример:** сотрудник подтверждает отправку черновика клиенту A. Tool-result предлагает «для проверки» добавить адрес B; backend отклоняет вызов, потому что digest и получатель отличаются. Отказ модели в чате не заменяет проверку отсутствия письма в outbox. При timeout действие получает `outcome unknown` до readback; слепая повторная отправка запрещена. Owner инструмента хранит минимальный audit `{action_id, principal, policy revision, approval digest, result/readback ref}`, без текста письма и токенов. См. [34](../34-ai-agents-runtime-procedure.md).

<a id="63-rag-sistemy"></a>

### 6.3. RAG-системы

Документы для RAG индексируются только из доверенных коллекций. Corpus poisoning проверяется при ingest-е. Между тенантами применяется строгая изоляция коллекций. Корпоративная информация K3-K4 не индексируется в системах с доступом для внешних пользователей.

<a id="64-fine-tuning-i-lora"></a>

### 6.4. Fine-tuning и LoRA

Адаптеры LoRA / QLoRA загружаются только из внутреннего реестра или из источников с подписью cosign. ModelScan / picklescan обязательны перед использованием. SafeTensors предпочитается PyTorch pickle.

<a id="65-dopusk-szenaria-background-jobs-i-otzyv"></a>

### 6.5. Допуск сценария, background jobs и отзыв

Для инструмента в корпоративном каталоге указываются назначение/scenario_id, владелец, разрешённые данные и действия, provider/retention, утверждённые tool/MCP endpoints, evidence status и срок пересмотра. `pending/unknown` не означает «разрешено»; `N/A` допустим с причиной. Не все IDE/agent-функции проходят через API gateway: отдельно проверяются terminal, downloads, setup/hooks, MCP, telemetry и фоновые jobs. Repository instructions и remote-agent descriptions — входные данные, а не источник дополнительных прав ([20](../20-code-assistants-security.md), [33](../33-ai-agents-security-overlay.md)).

Отзыв доступа, уход сотрудника и retirement сценария включают queued/running jobs, callbacks, делегированные credentials, shared sessions и кэши. Владелец фиксирует остановку и readback уже выполненных эффектов; закрытая вкладка не считается отменой работы. Изменение provider/region, назначения, tool permissions или incident требует пересмотра карточек и допуска; бюджет retry/background jobs проверяется по [22](../22-finops-ai.md).

<a id="7-otvetstvennost_"></a>

## 7. Ответственность

- **Сотрудник**: ознакомлен с политикой, соблюдает при использовании ИИ-инструментов.
- **Руководитель подразделения**: несёт ответственность за соблюдение политики в своей команде.
- **ML Lead / технический владелец**: обеспечивает архитектурное соответствие.
- **Security partner**: сопровождает threat modeling и проверки.
- **CISO**: утверждает политику, исключения, реагирует на инциденты.
- **DPO**: согласовывает операции с ПДн (класс K3).

<a id="8-isklucenia"></a>

## 8. Исключения

Исключения оформляются через процедуру Risk Acceptance: заявление руководителя подразделения с обоснованием, оценка рисков от ИБ, подпись CISO. Срок исключения: не более 6 месяцев с последующим пересмотром. Реестр исключений ведёт служба ИБ.

<a id="9-narusenia"></a>

## 9. Нарушения

| Уровень | Действие | Последствия |
|---------|----------|-------------|
| Низкий (единичный случай) | Обучение + предупреждение | Запись в журнале |
| Средний | Ограничение доступа к ИИ-инструментам на 30 дней | Внутреннее расследование |
| Высокий (утечка ПДн) | Дисциплинарное взыскание, уведомление РКН при необходимости, расследование ИБ | Возможное применение мер по 152-ФЗ и Трудовому кодексу |

<a id="10-peresmotr"></a>

## 10. Пересмотр

- Регулярный пересмотр: раз в 12 месяцев.
- Внеплановый: при изменении регулирования (152-ФЗ, ФСТЭК, ЦБ, новые постановления), появлении новых типов моделей или инцидентов.

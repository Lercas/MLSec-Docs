# IR-02. Model Extraction / Theft

> Severity: SEV1 (Critical), если модель Tier 1 или содержит КТ. SEV2 по умолчанию для Tier 2-3.
>
> SLA containment: 15 минут (SEV1) / 1 час (SEV2). SLA полного закрытия: 10 рабочих дней.

<a id="1-opredelenie-i-priznaki"></a>

## 1. Определение и признаки

Model Extraction / Theft: несанкционированное восстановление параметров, архитектуры или поведения модели либо кража её артефакта. Основные векторы: (а) query-based extraction через API (обучение суррогата на predictions), (б) кража артефакта (веса, ONNX, GGUF) из Model Registry / S3 / Git LFS. Смежные ветви расследования: membership inference, model inversion и раскрытие system prompt / инструкций. Они требуют отдельного подтверждения источника раскрытых сведений и сами по себе не доказывают кражу весов или воспроизведение поведения модели.

<a id="11-triggery-obnarujenia-ioc"></a>

### 1.1. Триггеры обнаружения (IoC)

- Аномальный всплеск запросов к inference endpoint с одного API-ключа / IP: RPS выше baseline на 10σ.
- Длительные серии запросов с однотипными префиксами (systematic exploration).
- Запросы с высокой энтропией входа, покрывающие пространство признаков (grid / random sampling).
- Запросы к logits / log_probs / top_k (а не только топ-1).
- Скачивание больших файлов (> 100 MB) из Model Registry / артефактного хранилища.
- Необычные `docker pull` или `git clone` ML-репозиториев из новых IP.
- Vault / KMS audit log: аномальный доступ к ключам шифрования моделей.
- Активность учётной записи после увольнения сотрудника (offboarding check).
- Внешний сигнал: обнаружение копии модели на HuggingFace / GitHub / darkweb / SaaS конкурента.
- DLP на исходящем трафике: выгрузка .bin / .safetensors / .gguf / .onnx.

<a id="12-istocniki-dannyh-dla-rassledovania"></a>

### 1.2. Источники данных для расследования

- API gateway / LLM gateway access logs (per-key RPS, запросы, latency, status).
- Inference service logs (тексты запросов, если логируются; иначе хеши).
- Kubernetes audit log (pod exec, kubectl port-forward).
- S3 / MinIO / Artifactory access logs (GET больших объектов).
- Vault / KMS audit log (использование ключей шифрования моделей).
- Git / GitLab audit log (clone, fork, push).
- SSO / IdP audit (сессии и токены сотрудника).
- Network flow logs / NetFlow / zeek (egress volumes).
- DLP агенты на endpoint (что копируется на флешки, в облака).

<a id="2-podgotovka-preparation"></a>

## 2. Подготовка (Preparation)

- [ ] Rate-limit на inference endpoint: RPS per-key, max запросов за сутки, жёсткие лимиты на запросы с `logits` / `logprobs`.
- [ ] API-ключи имеют срок жизни, scope, audit trail. Отсутствует «вечный» ключ для интеграций.
- [ ] Watermarking модели: встроенные статистические сигнатуры в веса (для PyTorch) или canary-ответы (для LLM).
- [ ] Фингерпринтинг выхода: поведенческие тесты, по которым можно опознать суррогатную копию.
- [ ] Шифрование артефактов at rest (KMS-envelope), подпись (cosign / Sigstore Model Transparency), доступ к приватным ключам через HSM.
- [ ] Настроены SIEM-правила: `ml-03-extraction-pattern`, `ml-04-artifact-exfiltration`.
- [ ] DLP на egress детектирует тензор-форматы (safetensors, GGUF, ONNX, .pt, .ckpt).
- [ ] Брендированный мониторинг darkweb / open-source листингов на появление корпоративных моделей.
- [ ] RACI по реагированию согласован с юр. службой (иск, cease-and-desist, правоохранители).

<a id="3-detection-amp-analysis"></a>

## 3. Detection & Analysis

<a id="31-triaj-l1-0-15-minut"></a>

### 3.1. Триаж (L1, 0-15 минут)

1. Подтвердить alert: какой детектор, какой endpoint / артефакт, какой источник (IP, key_id, user_id).
2. Определить затронутую модель и её Tier. Tier 1 = немедленная эскалация в L2 + CISO + юр. служба.
3. Проверить валидность API-ключа / учётной записи: действует ли, кем выписан, для какой интеграции.
4. Снять моментальный снимок: последние 24 ч логов по ключу / IP / артефакту.
5. Открыть инцидент `ML-EXTRACTION`, присвоить SEV.

<a id="32-analiz-l2-mlsec-analyst-15-60-minut"></a>

### 3.2. Анализ (L2 MLSec Analyst, 15-60 минут)

1. **Паттерн извлечения через API**:
   - Построить распределение запросов по времени, объёму, энтропии.
   - Проверить покрытие пространства признаков (for tabular: PCA на входах; for LLM: кластеризация эмбеддингов запросов).
   - Оценить пригодность собранных ответов для обучения суррогата с учётом типа задачи, доступных выходов и покрытия входов. Универсального порога числа запросов нет; серия запросов сама по себе не подтверждает обучение копии.
   - Проверить, запрашивались ли `logits` / `log_probs` / `top_k` (ускоряет extraction).
2. **Кража артефакта**:
   - Audit log S3 / Registry: кто, когда, какого размера объекты.
   - Сетевой egress: куда ушёл трафик, какой объём.
   - Endpoint DLP: копировался ли артефакт локально, на USB, в облако.
   - Vault / KMS: расшифровывал ли злоумышленник model blob.
3. **Prompt extraction** (для LLM):
   - Поиск в логах паттернов типа «repeat everything above», «print your instructions», «ignore previous», обфусцированных вариантов (base64, rot13, многоязычных).
   - Корреляция с выходами: были ли в ответе фрагменты system prompt.
4. **Атрибуция**:
   - Кто владеет API-ключом? Действующий ли сотрудник / контрагент?
   - Есть ли совпадение IP с ранее известными атакующими?
   - Соответствует ли паттерн известной угрозе (TTPs из MITRE ATLAS)?
5. **Оценка ущерба**:
   - Насколько полно восстановлены параметры (от 0 до 1)?
   - Содержит ли модель КТ / ПДн, восстановимые через inversion?
   - Потенциальные потери: конкурентное преимущество, violation лицензии вендора, утечка ПДн.

<a id="33-klassifikazia"></a>

### 3.3. Классификация

| Признак | SEV1 | SEV2 | SEV3 |
|---|---|---|---|
| Tier модели | 1 | 2 | 3-4 |
| Объём извлечения | Артефакт выгружен полностью, либо > 10^6 API запросов | Частичное извлечение, системный prompt получен | Единичные попытки, не успешные |
| Данные в модели | ПДн / КТ / конфиденциальные решения | Публичные или псевдо-публичные | Публичная модель |
| Подтверждение кражи | Копия найдена вовне | Сильные признаки, утечка не подтверждена | Только подозрение |

<a id="34-zepocka-atlas-i-dokazatel_stva"></a>

### 3.4. Цепочка ATLAS и доказательства

Для каждого наблюдаемого шага запишите время, principal / key_id, ресурс и revision модели, ссылку на evidence и статус `confirmed / suspected / unknown`. Ниже альтернативные ветви, а не обязательная последовательность одного инцидента. Выбранная техника описывает действие; вывод об ущербе требует отдельного свидетельства.

| Ветвь | Применимые техники ATLAS | Что подтверждать |
|---|---|---|
| Сбор ответов API для суррогата | AML.T0040 AI Model Inference API Access — доступ; AML.T0135 Outputs from AI Models — сбор выходов; AML.T0024 Exfiltration via AI Inference API — перенос информации через ответы API | Связанные request/response IDs, доступные выходы, получатель и систематичность сбора. AML.T0005.001 Replicate Behavior from Model Outputs добавляется при свидетельствах обучения / адаптации другой модели на этих выходах; сходство единичного ответа недостаточно |
| Копирование весов / датасета | AML.T0035 AI Artifact Collection — сбор артефактов; AML.T0025 Exfiltration via Cyber Means — подтверждённый вывод обычным сетевым каналом | Object/version ID, digest и фактически прочитанные байты, principal, destination, storage audit + egress. AML.T0037 Data from Local System уместна при поиске / сборе на локальной системе, а не при любом запросе к API. AML.T0044 Full AI Model Access требует полного white-box доступа к архитектуре, параметрам и онтологии |
| Вывод сведений об обучающих данных | AML.T0137 Training Data Information from AI Models; при установленном методе — AML.T0137.000 Infer Membership или AML.T0137.002 Invert AI Model | Проверяемая гипотеза о train, метод, контрольные данные и неопределённость. Правдоподобный текст не доказывает наличие записи в train; канал передачи маркируется отдельно |
| Получение скрытых инструкций | AML.T0085.003 System Instructions — сбор; AML.T0069.002 System Prompt — разведка инструкций / возможностей, если наблюдается именно она | Сверка раскрытых фрагментов с доверенной revision инструкций без тиражирования секретов в incident report. Утечка инструкций не равна извлечению параметров модели |

Collection (AML.TA0009) отделяйте от Exfiltration (AML.TA0010): чтение объекта ещё не показывает, куда он ушёл. AML.TA0005 — Execution; AML.T0048 — External Harms. Для Craft Adversarial Data используется AML.T0043, но в этот инцидент её включают только при наблюдаемом создании adversarial inputs, а не по факту extraction.

ID и смыслы сверены с [MITRE ATLAS v2026.10](https://github.com/mitre-atlas/atlas-data/releases/tag/v2026.10), проверка 13.11.2026. Матрица и дополнительные ветви — в [главе 23](../23-mitre-atlas-ru.md).

<a id="4-containment"></a>

## 4. Containment

<a id="41-nemedlennye-dejstvia-0-15-minut-ot-podtverjdenia-sev2"></a>

### 4.1. Немедленные действия (0-15 минут от подтверждения SEV2+)

1. **Отозвать API-ключ** подозреваемого клиента через LLM gateway / API gateway.
2. **Блокировать IP / подсеть** на WAF / API gateway, временно ограничить географию (geo-fencing).
3. **Ограничить раскрываемые сведения** в затронутом scope: отключить выдачу logits / logprobs, если API их предоставляет, пересмотреть лимиты. `top_k` часто управляет sampling, а не выдачей сведений; снижение temperature не является защитой от extraction.
4. **Rate-limit hardening**: временно ужесточить глобальные лимиты (например, 10 RPS per-key).
5. **Заблокировать доступ к артефакту**: revoke read в Model Registry / S3 bucket, отключить ссылку для shared access.
6. **Заморозить учётную запись сотрудника** (при подозрении на инсайдера): disable SSO, блокировать VPN, собрать устройство для экспертизы.
7. **Уведомить**: ML Tech Lead, CISO, юр. служба, AI Risk Committee.

<a id="42-takticeskie-dejstvia-15-min-4-casa"></a>

### 4.2. Тактические действия (15 мин - 4 часа)

1. Не подменять ответы рабочей модели автоматически: исследование canary / watermark проводить на отдельном согласованном endpoint. Это не возвращает уже скопированные данные.
2. При признаках компрометации KMS — согласовать отдельную ротацию и миграцию шифрования с владельцем ключей; смена credentials и re-encrypt решают разные задачи.
3. Менять signing trust root только при обоснованной компрометации и через процедуру отзыва / повторного допуска. Не переподписывать подозрительный артефакт как доверенный.
4. Усилить мониторинг в подтверждённом scope: IDs, объём, статус, получатель; содержимое сохранять адресно в защищённом evidence-store, с редактированной ссылкой в тикете.
5. Подключить SOC NTA на анализ egress за последние 30 дней.
6. Для финсектора / КИИ: уведомить ФинЦЕРТ / ГосСОПКА согласно процедурам.
7. Если могли быть раскрыты ПДн, привлечь DPO / юриста для проверки оснований уведомления и срока от выявления события по [главе 18](../18-ru-compliance-deep.md); присутствие ПДн в обучении само по себе не доказывает утечку.

<a id="5-eradication-amp-recovery"></a>

## 5. Eradication & Recovery

<a id="51-eradication-dni-1-5"></a>

### 5.1. Eradication (дни 1-5)

1. **Root cause**:
   - Компрометация ключа / учётной записи (phishing, утечка, переиспользование пароля)?
   - Злоупотребление легитимным доступом (инсайдер, подрядчик)?
   - Обход rate-limit (распределённая атака через разные ключи)?
   - Уязвимость в API (IDOR, нет проверки ownership)?
2. **Очистка компрометации**:
   - Ротировать все ключи / секреты / токены, к которым у злоумышленника мог быть доступ.
   - Пересоздать сервис-аккаунты, ротировать kubeconfig, webhook-секреты.
   - При подтверждённом затрагивании ключа шифрования — выполнить согласованную ротацию / re-encrypt с владельцем KMS. Это не отзывает уже выгруженную plaintext-копию.
3. **Форензика**:
   - Собрать образ диска / memory dump скомпрометированного endpoint (если инсайдер).
   - Сохранить необходимые логи за установленный период в защищённом хранилище; срок retention / legal hold определить с юристом, а не автоматически назначать 3 года.
4. **Юридические действия** (по решению юр. службы и CEO):
   - Claim на HuggingFace / GitHub (takedown DMCA, если применимо).
   - Cease-and-desist письмо.
   - Обращение в правоохранительные органы (ст. 272, 273 УК РФ: НСД, вредоносные программы; ст. 183: разглашение КТ).
   - Претензия сотруднику / контрагенту.

<a id="52-recovery-dni-3-10"></a>

### 5.2. Recovery (дни 3-10)

1. **Ужесточение API**:
   - Постоянные (не только тактические) rate-limits, per-key daily quota.
   - Обязательный OAuth / mTLS для доступа к высоко-критичным моделям.
   - Ограничить доступ к дополнительным выходам модели (например, logits / logprobs, если API их предоставляет) по роли и назначению.
   - Внедрить anomaly-based throttling (автоматический downgrade при аномалиях).
2. **Watermarking новой версии модели**: встроенные сигнатуры для идентификации утечек.
3. **Обновить Model Card**: зафиксировать факт инцидента, изменения в защите, рекомендации.
4. **Усилить мониторинг**: новые Sigma-правила, алерты SOC, threat intel feeds на появление модели.
5. **Переобучение** (опционально, по решению ML Tech Lead): если модель содержала ПДн / КТ и инверсия возможна, переобучить с DP / federated / с урезанным датасетом.

<a id="53-podtverjdenie-otzyva-i-granizy-userba"></a>

### 5.3. Подтверждение отзыва и границы ущерба

Запросы к модели, извлечение system prompt, inference обучающих данных и скачивание весов — разные наблюдения. Число запросов не доказывает полноту украденной модели; fidelity указывается только с описанием измерения. Статус «скачивание не подтверждено» не означает «данные точно не ушли».

| Путь доступа | Что проверяет владелец | Свидетельство |
|---|---|---|
| API key / OAuth session | Прежний credential больше не даёт доступ к затронутому ресурсу, refresh не выдаёт новый доступ | IAM owner: безопасный deny-test без скачивания модели |
| Presigned URL / CDN / cache | Фактическая доступность ранее выданной ссылки и механизм ограничения у конкретного storage | Storage owner: readback и остаточное окно доступа; ротация gateway key сама по себе ссылку не отзывает |
| Принятый export / batch job | Job остановлен или завершён; определён объект и получатель | Integration owner: внешний job ID, status, destination; при недоступном readback — `unknown` |
| Восстановленный endpoint | Запрещённый путь закрыт, легитимный клиент в разрешённом scope работает | Serving owner: парные negative / positive тесты |

Watermarking и переобучение новой версии не удаляют прежнюю копию у получателя. IC фиксирует отдельно подтверждённый выход данных, подозрение и остаточный риск. Источники и правила сохранения evidence: [общие условия IR](README.md), тематическая сверка **13.11.2026**.

<a id="6-post-incident-activity"></a>

## 6. Post-Incident Activity

<a id="61-obazatel_nye-artefakty-v-tecenie-15-rabocih-dnej"></a>

### 6.1. Обязательные артефакты (в течение 15 рабочих дней)

- [ ] Incident report с таймлайном, атрибуцией, оценкой ущерба.
- [ ] Обновлённая Model Card (раздел Security).
- [ ] Обновлённый threat model.
- [ ] Обновлённые SIEM-правила (IoC).
- [ ] Обновлённый adversarial / extraction test suite.
- [ ] Lessons Learned встреча с ML-командой, ИБ, DevOps, юр. службой.
- [ ] Финальная позиция юр. службы (судебные действия / отказ / settlement).
- [ ] Уведомления РКН, ФинЦЕРТ, ГосСОПКА по ситуации.

<a id="62-metriki-dla-ozenki"></a>

### 6.2. Метрики для оценки

- Время между первым аномальным запросом и алертом (Time to Detection).
- Число запросов до containment.
- Оценка степени извлечения модели (от 0 до 1).
- Потери (прямые и косвенные).
- Процент покрытия риска после внесённых улучшений.

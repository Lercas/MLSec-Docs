# Матрица соответствия: Приказы ФСТЭК 117 (ранее 17), 21, 31, 239

> Сопоставление мер защиты по Приказам ФСТЭК (117 (ранее 17), 21, 31, 239) с главами MLSec Recommendations применительно к ИИ-системам. Режимы и наборы требований различаются; внутренние K0-K4 / Tier не заменяют нормативную классификацию. Приказ ФСТЭК №17 (2013, защита ГИС) отменён; с 01.03.2026 действует Приказ №117 от 11.04.2025, с положениями об использовании ИИ. Точные пункты, изменения и классификацию проверяют по действующему тексту, не по этому краткому mapping.

<a id="oblast_-primenenia"></a>

## Область применения

| Приказ | Класс систем | Уровни |
|--------|--------------|--------|
| ФСТЭК 117 (ранее 17) | ГИС, иные ИС госорганов, ГУП, госучреждений на территории РФ; муниципальные ИС по п. 3 с оговоркой законодательства; принимающая ИС при потоке из ГИС — п. 2 | 1, 2, 3 классы защищённости ИС; это не K0–K4 данных |
| ФСТЭК 21 | Информационные системы персональных данных (ИСПДн) | УЗ1-УЗ4 |
| ФСТЭК 31 | Автоматизированные системы управления (АСУ ТП) | К1, К2, К3 |
| ФСТЭК 239 | Значимые объекты КИИ | 1, 2, 3 категории |

Изменения 137 — с 01.09.2026, кроме п. 7 приложения (новый п. 32 Требований), который вступит 01.03.2027 и не применяется как текущий в ноябре 2026.

Изменения 137 эти AI-пункты не меняют. «Доверенные технологии» — отсылка к Нацстратегии п. 5ц (сноски 17/25), не статус суверенной/национальной БФМ по 243-ФЗ и не автоматический допуск из-за российского ЦОД. Форматы/шаблоны ответов по п. 61 устанавливает оператор (обладатель информации); роли в правой колонке — внутреннее распределение функций. Конкретные механизмы — способы реализации/проверки, а не дословно предписанный набор продуктов. Карта применимости и границы п. 1–7: [18, §3.1.1](../18-ru-compliance-deep.md). Проверенный источник не доказывает соответствие конкретной системы.

Для аудита строку дополняют точным актом/редакцией/пунктом, объектом, обоснованием применимости и evidence. Продукт, DLP-слой, MIG или подпись cosign не являются сами по себе нормативной мерой, сертификатом либо оценкой соответствия.

## Интеграция в жизненный цикл ИСПДн

Соблюдение ФСТЭК 21 при внедрении ИИ-системы:

```
1. Проектирование (до внедрения)
   → Оценка вреда / организационные обязанности по применимым нормам РФ
   → Модель угроз (Методика ФСТЭК от 05.02.2021) + определение УЗ по ПП РФ 1119
   → PIA — внутренний формат; DPIA по GDPR и оценка вреда РФ не взаимозаменяемы
   → [PIA-TEMPLATE] + [THREAT-MODEL-TEMPLATE]

2. Внедрение
   → Применение мер по УЗ 1-4 + Аттестация (при необходимости)
   → [FSTEK-AUDIT-CHECKLIST]

3. Эксплуатация
   → Регулярный аудит + Пентест + АНЗ
   → Пересмотр моделей угроз при изменении ландшафта

4. Вывод из эксплуатации
   → Проверка оснований / сроков, уничтожение затронутых копий и производных + подтверждение
   → Отдельно учесть законное сохранение evidence, backups и tombstones при restore
```

## Пример применимости: один AI-сервис, несколько независимых режимов

**Ситуация:** inference работает внутри государственной ИС, получает ПДн и использует agent tool в процессе, связанном с КИИ. Не следует выбирать один «самый строгий класс» и считать остальные режимы автоматически закрытыми.

| Проверяемый вопрос | Решение и предлагаемый контроль | Evidence | Открытый аспект |
|---|---|---|---|
| Каков объект и действующий scope 117? | Установить владельца, границы ИС и применимый пункт; включить AI runtime / очередь / внешних подрядчиков | Сохранённый текст актуальной редакции, схема потоков и подписанное rationale | Пока полного текста / пункта нет, строка нормативного mapping `unknown` |
| Есть ли обработка ПДн и какой УЗ? | Обосновать цели, категории / субъектов и УЗ; выбрать меры по режиму ИСПДн | Документы оператора + data-flow, current ACL и тесты batch/cache/fallback | Внутренний K3 не доказывает УЗ1; маскирование не доказывает анонимность |
| Связан ли ML с категорированным объектом КИИ? | Определить объект, функции и применимость 239; проверить доступ tools к значимому объекту | Документы категорирования, scoped measure register, independent executor deny tests | Само наличие ML не делает модель отдельным ЗОКИИ |
| Как квалифицировать событие для уведомления? | По [зарегистрированному порядку ФСБ №547](https://minjust.consultant.ru/files/57932), пп. 3–4, определить объект / событие / получателя | Event timeline, момент обнаружения, affected object, адресаты и receipt; полный разбор в главе 18 | Нельзя назначать универсальный срок всем событиям / организациям |

**Проверка evidence на границе:** временно отозвать доступ service account к тестовому документу и заблокировать обязательный policy service. Проверить поиск, cache, agent tool, queued retry и direct egress; clean разрешённый запрос должен пройти, запрещённый не должен иметь внешнего эффекта. Сохранить active revisions и минимальные audit metadata, проверить restore и доставку evidence. Это техническая проверка выбранных мер; она не является аттестацией ИС или подтверждением сертификата средств защиты.

**Замыкание нормативной строки:** акт/редакция/пункт → объект и rationale → проектная мера → deployment revision → test/outcome → решение ответственного. Если средство требует оценки соответствия, проверяются конкретное исполнение, версия, область/срок сертификата и условия эксплуатации. Open-source инструмент или запись в этой таблице не подменяет такую проверку.

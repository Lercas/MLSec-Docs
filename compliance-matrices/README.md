# Compliance Matrices

> Сквозные матрицы соответствия между методикой MLSec Recommendations и внешними стандартами, регуляциями, каталогами угроз. Каждая матрица отвечает на один вопрос: "где в методике адресован конкретный пункт стандарта?". Матрицы служат навигацией и основой для проверки применимости; ссылка на главу или шаблон не доказывает исполнение требования.

<a id="format-matriz"></a>

## Формат матриц

Каждый файл содержит таблицу вида:

| Пункт стандарта | Описание | Глава методики | Практики | Артефакты |
|-----------------|----------|----------------|----------|-----------|

- **Пункт стандарта**: идентификатор (LLM01, AML.T0051, Govern 1.1, A.5.2, ст. 15, ФСТЭК-ИАФ и т.п.).
- **Описание**: редакторский пересказ темы источника, не нормативная цитата; для аудита нужен проверенный пункт и редакция.
- **Глава методики**: ссылка на главу или раздел документа, где рассматривается.
- **Практики**: предлагаемые автором меры / контроли / процессы; стандарт не обязательно предписывает указанный продукт.
- **Артефакты**: шаблоны, скрипты, чек-листы в этом репозитории.

<a id="prinzipy-postroenia"></a>

## Принципы построения

1. **Границы**: это выбранные связи, не доказательство полного покрытия документа. Пропущенный пункт не становится «неприменимым»; для полного аудита нужен реестр всех требований выбранного scope.
2. **Двунаправленность**: матрицы читаются и от стандарта к методике, и от методики к стандарту.
3. **Актуальность**: при выходе обновлений стандартов матрицы пересматриваются в рамках процесса review.
4. **Единообразие**: один и тот же контроль может появляться в нескольких матрицах; это ожидаемо.

<a id="primenimost_-i-dokazatel_stva-pat_-raznyh-polej"></a>

## Применимость и доказательства: пять разных полей

Обновлено 13.11.2026. Нормативный текст, guidance, каталог атак и draft имеют разный статус. OWASP и ATLAS не являются законами; NIST RMF / GenAI Profile — добровольные framework/profile. Новая AML taxonomy SP 2400-102 E2026 остаётся Initial Public Draft и не заменяет final RMF.

| Поле рабочей записи | Что фиксируется | Пример ошибки |
|---|---|---|
| **Источник / статус** | Организация, название, редакция, конкретный пункт, проверенный текст / draft / guidance | Считать публичный ISO abstract проверкой Annex A |
| **Применимость / трактовка** | Роль, объект, intended use, территория, дата, обоснование и владелец решения | Автоматически приравнять внутренний Tier к high-risk AI / УЗ ИСПДн |
| **Предлагаемый контроль** | Проектное решение, target и policy revision, условия отказа | Приписать стандарту обязательный Rilio, DLP-слой или SLSA level |
| **Проверяемое evidence** | Digest release, test ID / среда / дата, runtime readback, outcome, reviewer | Принять пустой шаблон или успешный HTTP за доказательство enforcement |
| **Остаток / неизвестное** | Непроверенный режим, ограничение выборки, срок исключения, ответственный | Преобразовать unknown в pass или N/A |

Статусы строки: **не оценено → применимость установлена → контроль спроектирован → проверен в scope → наблюдается в эксплуатации**. `N/A` требует обоснования; `blocked/unknown` не входят в число подтверждённых контролей. Число ссылок в справочнике не пересчитывается в процент соответствия.

**Пример замыкания evidence: отозван доступ к RAG-документу.** В источнике OWASP LLM08:2025 — риск vector/embedding weaknesses; текущий ACL контекст определяется системой, а не самим OWASP ID. Наш контроль: авторизация до retrieval и перед выдачей, инвалидация кэша/сессии, проверка ACL revision. Evidence: один subject/document/release trace, успешное чтение до отзыва, запрет после отзыва из vector search, cache и memory, отсутствие canary в ответе/логах; повтор после restore. Ограничение: эти проверки не оценивают всю privacy обученных весов. Практика: [16](../16-ml-attacks-rag-multimodal.md), [24](../24-vector-db-security.md).

**Рабочая запись evidence** (учебная схема, не результат выполненной проверки):

```yaml
assessment:
  source: "OWASP Top 10 for LLM Applications 2025"
  source_id: "LLM08:2025"
  source_status: "guidance"
  applicability_rationale: "RAG выдаёт документы с разграничением доступа"
  control: "server-side document ACL + revoke across cache/memory"
  subject_digest: "<deployment-and-policy-digest>"
  evidence_refs: []
  required_checks:
    - "permitted read succeeds"
    - "revoked access denied across retrieval/cache/memory/restore"
  status: "not_evaluated"
  uncovered: "training memorization; другие providers/tools"
  owner: "<responsible-role>"
  reviewed_at: null
```

Пустой `evidence_refs`, шаблонный digest и `reviewed_at: null` оставляют эту запись неоценённой. После проверки сохраняются immutable report references, observed runtime revision, исход и ограничения; изменение subject вызывает impact review, а не автоматическое копирование pass.

**Пример применимости: внешний API модели в банке.** Сначала определить роль и обработку данных, договор/маршруты/субподрядчиков; отдельно применимость 152-ФЗ, банковских требований и EU AI Act. Затем проверить реальные fallback, retries, batch и agent tools. Успешный ответ API и наличие ISO-сертификата поставщика не заменяют основания передачи и доказательства выбранного исполнения. Карта решения: [18](../18-ru-compliance-deep.md), состояние release: [01 §3.5](../01-overview-architecture.md).

<a id="kak-pol_zovat_sa-dla-audita"></a>

## Как пользоваться для аудита

1. Выбрать релевантный стандарт из списка.
2. Пройти по таблице, отмечая, какие пункты применимы к конкретной ИИ-системе.
3. Для каждого применимого пункта:
   - Открыть указанную главу методики.
   - Проверить, реализованы ли перечисленные практики.
   - Собрать артефакты (шаблоны, журналы, политики).
4. Составить gap-анализ: что покрыто, что нет, что требует доработки.
5. Приложить матрицу к отчёту по аудиту.
